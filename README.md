# Сетевое ПО — лабораторные работы

**Группа:** ИА332  
**Вариант:** 5 (идентификатор в репозитории курса: `s05`)  
**Ресурс по варианту для ЛР1:** `bookings` с дополнительным полем `date` (строка).  
Сервис в индивидуальном задании: `bookings-svc-s05`, порт **8152** (см. `variants/332/s05/week-01.json` в репозитории с заданиями).

## Запуск

### Локально

```bash
pip install -r requirements.txt
uvicorn main:app --reload --port 8000
```

Примеры:

- `GET http://127.0.0.1:8000/bookings` — список бронирований  
- `POST http://127.0.0.1:8000/bookings` — создать (`name`, `date`), ответ **201** и тело с полем `id`  
- `GET http://127.0.0.1:8000/bookings/{id}` — одно бронирование  

### Docker Compose

```bash
docker compose up --build
```

API будет доступен на хосте по адресу `http://127.0.0.1:8152` (проброс на порт 8000 в контейнере).

## Лабораторная работа 1 — ответы на контрольные вопросы

Вопросы из методички (`questions.md`, неделя 1).

1. **В чём разница между «ресурсом» и «коллекцией» в REST?**  
   Коллекция — это множество однотипных сущностей (например, все бронирования), к которому обращаются по одному URL (`/bookings`). Отдельный ресурс — один конкретный экземпляр с собственным идентификатором (`/bookings/3`). То есть коллекция — «тип + все элементы», ресурс в узком смысле — один элемент.

2. **Почему для создания используют `POST` и код `201`, а не `200`?**  
   `POST` семантически означает «создать подчинённый ресурс» (или выполнить действие), а код **201 Created** явно говорит клиенту: «сущность появилась», в отличие от **200 OK**, который чаще означает «вот данные, ничего нового не создавалось». Так проще строить кэши, логику повторных запросов и контракт API.

3. **Что такое идемпотентность? Какие методы идемпотентны?**  
   Идемпотентность — свойство запроса: повтор с теми же параметрами даёт тот же эффект на состоянии сервера, что и один вызов (для клиента результат предсказуем). Идемпотентными считают **GET**, **HEAD**, **PUT**, **DELETE** (и **OPTIONS**, **TRACE**). **POST** по умолчанию не идемпотентен, если специально не спроектировано иначе.

4. **Почему `id` обычно выдаёт сервер в ответе на `POST`?**  
   Чтобы гарантировать уникальность и единый формат идентификатора, избежать гонок и коллизий, когда несколько клиентов создают объекты одновременно, и чтобы клиент сразу знал, по какому адресу потом запрашивать ресурс (`GET /.../{id}`).

5. **Что такое «контракт API» и зачем его соблюдать?**  
   Контракт — соглашение о форматах URL, методах, кодах ответа, полях тел запросов/ответов. Его соблюдение позволяет независимо развивать клиент и сервер, писать тесты и интеграции без сюрпризов.

6. **Зачем спецификация вроде OpenAPI (Swagger)?**  
   Это машиночитаемое описание API: из него генерируют документацию, моки, клиентские SDK, проверяют совместимость версий и автоматизируют тестирование, чтобы команда говорила на одном языке о поведении сервиса.
