## Лабораторная работа 1 — ответы на контрольные вопросы

Вопросы из `questions.md` (неделя 1).

1. **В чём разница между «ресурсом» и «коллекцией» в REST?**  
   Коллекция — множество сущностей по одному URL (`/bookings`). Отдельный ресурс — один объект (`/bookings/3`).

2. **Почему для создания используют `POST` и код `201`, а не `200`?**  
   `POST` обозначает создание; **201 Created** явно фиксирует появление новой сущности, в отличие от обычной выдачи данных (**200**).

3. **Что такое идемпотентность? Какие методы идемпотентны?**  
   Повтор запроса не меняет состояние сильнее одного раза. Идемпотентны **GET**, **HEAD**, **PUT**, **DELETE** (и служебные **OPTIONS**, **TRACE**). **POST** по умолчанию не идемпотентен.

4. **Почему `id` выдаёт сервер в ответе на `POST`?**  
   Для уникальности id и чтобы клиент сразу мог вызывать `GET /.../{id}`.

5. **Что такое «контракт API»?**  
   Соглашение о URL, методах, кодах и форматах тел запросов и ответов.

6. **Зачем OpenAPI (Swagger)?**  
   Машиночитаемая спецификация для документации, клиентов и проверки совместимости версий.

## Лабораторная работа 2 — ответы на контрольные вопросы

Вопросы из `questions.md` (неделя 2).

1. **Чем `PUT` отличается от `PATCH`? Какой идемпотентен?**  
   `PUT` — полная замена ресурса по URL, считается **идемпотентным**. `PATCH` — частичное обновление; идемпотентность зависит от реализации.

2. **Коды ошибок:**  
   **400** — некорректный запрос в целом; **422** — ошибка валидации тела (в FastAPI/Pydantic); **401** — нет аутентификации; **403** — доступ запрещён; **404** — ресурс не найден.

3. **Зачем негативные тесты?**  
   Проверяют, что при ошибочных данных или отсутствующем id сервис возвращает ожидаемые коды, а не «успех».

4. **Почему ошибки в JSON?**  
   Структурированный ответ удобно разбирать клиентам и логировать.

5. **Обратная совместимость и валидация**  
   Совместимость — старые клиенты не ломаются при обновлении API. Новые обязательные поля ужесточают валидацию и могут сломать старых клиентов, поэтому поля добавляют осторожно (опциональные поля, версии API).

## Лабораторная работа 3 — ответы на контрольные вопросы

Вопросы из `questions.md` (неделя 3).

1. **Forward proxy и reverse proxy**  
   **Forward** — клиент явно направляет трафик через прокси «к интернету»; прокси выступает от имени клиента. **Reverse** — клиент обращается к прокси как к целевому серверу, а прокси перенаправляет запросы на внутренние сервисы; для клиента виден один вход (шлюз).

2. **Что такое upstream в Nginx?**  
   Именованная группа бэкенд-серверов (`upstream`), на которые `proxy_pass` пересылает запросы после маршрутизации.

3. **Зачем скрывать реальные IP и порты сервисов?**  
   Уменьшается поверхность атак, проще менять топологию и масштабировать сервисы за шлюзом без смены контракта для клиента.

4. **Задачи API Gateway кроме маршрутизации (примеры)**  
   Терминация TLS; аутентификация и rate limiting; агрегация ответов; канареечные релизы.

5. **Если упал Gateway?**  
   Клиент теряет единую точку входа. Защита: несколько экземпляров за балансировщиком, health-checks, автоматический failover, мониторинг.

## Лабораторная работа 4 — ответы на контрольные вопросы

1. **Почему нельзя одним `BEGIN … COMMIT` охватить несколько сервисов?**  
   У каждого сервиса своя БД и граница транзакции; нет общего менеджера блокировок. Распределённые двухфазные коммиты возможны, но дороги, хрупки и плохо сочетаются с автономией микросервисов.

2. **Оркестрация и хореография**  
   **Оркестрация** — центральный координатор вызывает шаги саги по очереди. **Хореография** — сервисы реагируют на события сами. Проще начать с оркестрации; при росте числа сервисов хореография может лучше масштабироваться, но сложнее отлаживать.

3. **Компенсирующая транзакция**  
   Логическое «откатное» действие после успешного шага: например, вернуть товар на склад после отмены оплаты.

4. **Ошибка компенсации**  
   Да, может завершиться ошибкой; тогда применяют **retry**, очереди повторных попыток и ручную сверку (reconciliation).

5. **Согласованность в конечном счёте**  
   Реплики и сервисы временно расходятся в данных, но без новых обновлений со временем сходятся к одному согласованному виду.

## Лабораторная работа 5 — ответы на контрольные вопросы

1. **GraphQL vs REST**  
   В GraphQL клиент одним запросом выбирает поле-граф; в REST набор фиксированных эндпоинтов и представлений.

2. **SDL**  
   Язык описания схемы GraphQL (типы, поля, query/mutation/subscription).

3. **Query и Mutation**  
   Query предназначена для чтения, mutation — для изменений. На одном уровне запроса GraphQL несколько полей могут выполняться параллельно, если не задана последовательность зависимостей; мутации обычно выполняются последовательно в рамках одного запроса (правило сервера).

4. **Резолвер**  
   Функция, вычисляющая значение поля; её вызывает рантайм GraphQL при разборе запроса.

5. **N+1 и DataLoader**  
   DataLoader батчит и дедуплицирует загрузки связанных сущностей, чтобы не делать отдельный запрос к БД на каждое поле.

6. **Кэш HTTP и GraphQL**  
   Чаще один URL и POST с разным телом — ключ кэша неочевиден; кэширование переносят на уровень приложения (Apollo, persisted queries).

## Лабораторная работа 6 — ответы на контрольные вопросы

1. **Зачем `variables`?**  
   Чтобы отделять текст запроса от данных, избежать инъекций и кэшировать запросы с разными параметрами без конкатенации строк.

2. **Поля JSON-запроса GraphQL**  
   Как минимум `query`; часто ещё `variables` и опционально `operationName`.

3. **Один endpoint**  
   Вся семантика в теле запроса; проще версионировать схему и не плодить URL под каждую комбинацию ресурсов.

4. **Поле `errors` и `data` вместе**  
   `errors` — частичные сбои резолверов; часть полей может прийти в `data`, часть — в `errors` (partial success).

5. **HTTP 200 с ошибками GraphQL**  
   Транспорт успешен, логика — в `errors`; клиент обязан разбирать тело, а не только статус.

6. **Типизированные клиенты**  
   Генерация типов, автодополнение, меньше опечаток в полях по сравнению с «сырыми» строковыми запросами.

## Лабораторная работа 7 — ответы на контрольные вопросы

1. **Зачем `.proto`?**  
   Единый контракт для разных языков и версий; код сообщений генерируется и остаётся согласованным.

2. **Unary RPC**  
   Один запрос — один ответ; похож на вызов REST-метода с телом запроса и ответом.

3. **Эффективность gRPC**  
   Бинарный protobuf меньше по размеру, меньше парсинг JSON; HTTP/2 мультиплексирует соединения.

4. **Совместимость в Protobuf и номера полей**  
   Номера стабильны при эволюции схемы: можно добавлять поля, сохраняя чтение старыми клиентами (при соблюдении правил).

5. **Stub и Servicer**  
   Stub — клиентский объект вызовов; Servicer — абстрактный базовый класс сервера, который реализует бизнес-логика RPC.

6. **REST vs gRPC**  
   REST для публичного HTTP API и кэшей; gRPC для внутренних высоконагруженных вызовов между сервисами.

## Лабораторная работа 8 — ответы на контрольные вопросы

1. **Server Streaming**  
   Один вызов RPC, поток ответных сообщений; пример — лента событий или лог в реальном времени.

2. **Стриминг vs большой список**  
   В стриминге элементы приходят по мере готовности и можно начать обработку раньше; один большой ответ требует полной сборки на сервере и разового переноса.

3. **Метрики**  
   Задержка (latency), пропускная способность (throughput), загрузка CPU, ошибки, использование памяти.

4. **Переиспользование Channel**  
   Канал дорог в установке; повторное использование даёт честный замер и близко к продакшену.

5. **Когда REST удобнее**  
   Публичный интернет, отладка через curl, кэширование CDN, когда важна человекочитаемость JSON.

6. **Head-of-Line Blocking**  
   В HTTP/1.1 ответы на одном соединении шли строго по очереди; HTTP/2 мультиплексирует потоки, gRPC это использует.

## Лабораторная работа 9 — ответы на контрольные вопросы

1. **Зачем signaling при P2P**  
   Нужно обменяться SDP и ICE-кандидатами до установки прямого канала; браузеры не знают адрес собеседника заранее.

2. **NAT**  
   Переводит частные IP в общий; внешний узёл не может инициировать соединение к клиенту без обхода (STUN/TURN, ICE).

3. **STUN и TURN**  
   STUN помогает узнать публичный адрес и пробить простой NAT; TURN ретранслирует весь медиатрафик, когда прямой путь невозможен.

4. **ICE Candidate**  
   Возможный путь доставки медиа (IP, порт, протокол), собираемый ICE-агентом.

5. **UDP в WebRTC**  
   Нужна низкая задержка и устойчивость к потерям для медиа; TCP head-of-line blocking хуже для реалтайма.

6. **SDP**  
   Формат описания медиа-сессии: кодеки, порты, атрибуты транспорта, используемый при установке соединения.

## Лабораторная работа 10 — ответы на контрольные вопросы

1. **Слой Docker и порядок команд**  
   Каждая инструкция создаёт слой; неизменяемые шаги (зависимости) выносят вверх, чтобы кэш не сбрасывался при правке кода.

2. **Multi-stage**  
   Сборка в «толстом» образе, в финал копируют только артефакты — меньше размер и поверхность атак.

3. **`.dockerignore`**  
   Исключает лишние файлы из контекста сборки (venv, кэши), ускоряет build и уменьшает риск утечки секретов.

4. **`CMD` и `ENTRYPOINT`**  
   ENTRYPOINT задаёт неизменяемую обёртку процесса; CMD — аргументы по умолчанию, которые легче переопределить при `docker run`.

5. **`COPY` vs `ADD`**  
   COPY только копирует; ADD тянет URL и автораспаковку архивов — чаще избыточен и менее предсказуем.

6. **`0.0.0.0` в контейнере**  
   Слушать нужно на всех интерфейсах контейнера, иначе проброс портов с хоста на `127.0.0.1` внутри контейнера не сработает.
