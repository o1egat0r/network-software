## Текущая версия кода (лабораторная 2)

Ресурс **`comments`**, поля тела запроса: **`name`**, **`author`**. Реализованы **GET** `/comments`, **POST** `/comments` (201), **GET** `/comments/{id}`, **PUT** `/comments/{id}` (полная замена), **DELETE** `/comments/{id}` (204 при успехе). Неверный тип полей даёт **422** (Pydantic); отсутствующий id — **404**.

## Лабораторная работа 1 — ответы на контрольные вопросы

Вопросы из `questions.md` (неделя 1).

1. **В чём разница между «ресурсом» и «коллекцией» в REST?**  
   Коллекция — множество сущностей одного типа по одному URL (`/bookings`). Отдельный ресурс — один объект с уникальным URL (`/bookings/3`).

2. **Почему для создания используют `POST` и код `201`, а не `200`?**  
   `POST` обозначает создание (или действие), **201 Created** явно сигнализирует о появлении новой сущности, что отличается от обычной выдачи данных (**200**).

3. **Что такое идемпотентность? Какие методы идемпотентны?**  
   Повтор запроса не меняет состояние сильнее, чем один раз. Идемпотентны **GET**, **HEAD**, **PUT**, **DELETE** (и служебные **OPTIONS**, **TRACE**). **POST** по умолчанию не идемпотентен.

4. **Почему `id` выдаёт сервер в ответе на `POST`?**  
   Для уникальности, единообразия и чтобы клиент сразу мог вызывать `GET /.../{id}` без собственной генерации id.

5. **Что такое «контракт API»?**  
   Соглашение о URL, методах, кодах и форматах тел; его соблюдение стабилизирует интеграции.

6. **Зачем OpenAPI (Swagger)?**  
   Для формальной спецификации, документации, генерации клиентов и проверки совместимости версий.

## Лабораторная работа 2 — ответы на контрольные вопросы

Вопросы из `questions.md` (неделя 2).

1. **Чем `PUT` отличается от `PATCH`? Какой идемпотентен?**  
   `PUT` обычно означает полную замену представления ресурса по указанному URL; ожидается идемпотентность (повторный `PUT` с тем же телом — то же состояние). `PATCH` — частичное изменение; на практике идемпотентность зависит от семантики, но классический **PUT** считают идемпотентным.

2. **Какие коды ошибок и когда?**  
   **400** — некорректный запрос в целом (синтаксис, семантика на уровне приложения без привязки к полям). **422** (в стеке FastAPI для Pydantic) — тело не прошло валидацию (типы, обязательные поля). **401** — не аутентифицирован. **403** — аутентифицирован, но доступ запрещён. **404** — ресурс по данному пути или id не найден.

3. **Зачем негативные тесты?**  
   Они проверяют граничные случаи и ошибки: сервис не должен «молчать» с 200 при неверных данных или отсутствующем объекте.

4. **Почему ошибки в JSON, а не простым текстом?**  
   Структура (поля кода, сообщения, деталей валидации) позволяет клиентам программно обрабатывать сбои, локализовать UI и логировать единообразно.

5. **Обратная совместимость API и валидация**  
   Совместимость — старые клиенты продолжают работать при обновлении API. Строгая валидация защищает от «грязных» данных, но новые обязательные поля ломают старых клиентов; поэтому поля часто добавляют как необязательные со значениями по умолчанию или версионируют API.
